# 多频率 MCAP 录制

MCAP 是可选原始录制格式，默认仍为原来的 30 Hz HDF5。现有网页和终端标注流程保持不变。

## 安装与启动

在 `gello_software` 中执行：

```bash
uv sync --frozen --extra yam --extra realsense --extra mcap
scripts/teleop --recording-format mcap --check
scripts/teleop --recording-format mcap --state-hz 200 --control-hz 200 --task-name pick_banana
```

- `--control-hz`：实际生成和发送 action 的目标频率，30–200，默认 30。
- `--state-hz`：反馈质量目标频率，30–500，默认 200。保存全部原生反馈，不补帧；实际频率可能高于目标。批量读取频率最多 50 Hz，与保存频率不同。
- 相机按原 YAML 的 fps 工作，默认 30；三个视角独立写入，不等相互对齐。
- CAN 控制线程保存最近 2048 个完整反馈快照，录制端按时间戳分批读取，不另开 CAN 连接。缓冲区溢出会中止录制，不默默漏掉中间反馈。
- 软件测试不能证明本机能达到 200 Hz；需要实际数采验收。终端每秒显示本条累计实测频率和控制调度错过的周期数；图像编码、RPC、磁盘仍会影响吞吐。

守护协议升级为 5，旧守护进程会被拒绝复用。先完成支撑和正常停机，再启动新版本；不要在机械臂使能时强杀旧守护进程。当前基线标签仍可用于原版本回退。

## 文件和数据语义

路径：`data/任务名/mcap/{success,fail,.in_progress}/episode_编号_UUID.mcap`。与旧 HDF5 编号和目录隔离。

| Topic | 内容 |
|---|---|
| `/session` | schema 版本、目标频率、臂顺序、相机配置、起始时间 |
| `/left/state`、`/right/state` | 从臂 position、velocity、effort，各 7 维，最后一维为归一化夹爪 |
| `/third/state`、`/fourth/state` | 四臂模式额外反馈 |
| `/action/requested` | 本控制周期映射后的主臂目标，双臂 14 维／四臂 28 维 |
| `/action/accepted` | 守护进程接受并限幅后的目标，以及是否限幅 |
| `/cameras/视角/rgb` | 原分辨率 H.264 视频访问单元，帧号、关键帧标记、设备及主机时间 |
| `/cameras/视角/depth` | 开启深度时的 uint16 小端原始像素 |
| `/events` | 检测到的相机帧号缺口 |

action 是绝对关节位置目标，不是实测位置，也不是电机最终执行扭矩。accepted 表示守护层接受的目标，底层电机控制仍可能施加关节限位。两路 action 的消息序号对应同一次控制；相同位置的重复命令仍是实际发送的控制事件，不伪称新主臂反馈。

每条消息包含 `source_time_ns`、`record_time_ns`、`data`：MCAP `publish_time` 对应 source，`log_time` 对应记录接收时间。state 的 source 来自底层反馈快照（当前使用首个电机反馈的主机时间，并非所有关节硬件同步采样）；action 使用请求发送／守护接受时间。图像保留设备时间域，并把主机单调时间通过会话起点映射为 Unix 纳秒。

这是主机侧时间关联，不是相机硬件同步。系统时钟回跳、未来时间或反馈过期会影响质量，需要检查；不能只按数组下标对齐。

## 与 ABC-130k 的关系

借鉴独立 topic、独立时序、原始数据与训练格式分离。保留 `yam.multirate.v1` profile 和 JSON 消息封装；新文件的 session `schema_version=2`，RGB `encoding=h264`，base64 内容是 Annex B 压缩访问单元。仍不是 ABC-130k 的 Protobuf schema，不能直接送入其导出脚本。旧版 `rgb8`、`z16` 和 PNG 数据仍可读取、检查和导出。

H.264 使用 libx264、CRF 18、veryfast、yuv420p，每 30 帧以内一个关键帧，无 B 帧；每个相机有独立编码上下文，放在独立进程中。它是有损视频压缩，深度仍为无损 uint16。编码器在从臂保持时预热，再开始同步，避免启动编码器阻塞控制。每个输入帧必须立即对应一个压缩包，保留原始纳秒时间戳，不重采样为固定帧时间。

控制线程只向有界队列入队；MCAP 写入在独立线程，编码失败、超时或队列满会明确中止。正常保存会检查编码器尾部，再写完文件。导出必须顺序解码视频，包括对齐时未选中的帧，不能直接从任意 P 帧开始解码。

200 Hz 控制使用缓存的关节数量、动作与观测合并 RPC、复用双臂工作线程及单调时钟绝对周期；超时跳过已错过的周期，不突发补发动作。安全限幅和 200 ms 命令过期保持策略不变。当前升级不自动停止正在运行的旧守护进程。

## 故障与保存

- 相机短暂缺帧：其他相机及 state/action 继续记录，帧号缺口写事件；任一相机连续 1 秒无新帧时结束录制并请求保持。
- state：按严格递增时间戳保存原生反馈；缓冲溢出、超过 200 ms 无新反馈、时间戳回退、缺臂、NaN 或维度错误会中止。
- 主臂仍使用已有 200 ms 反馈过期检测。
- MCAP 控制采用时间限幅，按原 30 Hz 下的速度尺度换算；连续限幅按时间累计。控制命令超过 200 ms 未更新会请求保持，即使心跳仍正常。
- 停止或异常先请求保持，再暂停采集和处理磁盘。相机、state 生产线程在结束本条时停止，不把标注等待时间录进去。
- 正常保存先排空队列、写完 MCAP、fsync，再发布到 success/fail；发布失败保留源文件供重试。
- 未完成文件重启后可以 f 恢复为失败或 d 废弃。恢复只复制校验通过的消息，遇到损坏／截断停止，尾部 chunk 可能丢失，不补造数据。
- 文件恢复不代表该条具备完整训练数据；还需要质量检查。原始文件的成功／失败由所在目录表示。

## 检查和导出

```bash
scripts/mcap inspect /完整路径/episode_0001_UUID.mcap
scripts/mcap export-hdf5 /完整路径/episode_0001_UUID.mcap \
  --output-root /独立导出目录 --task-name pick_banana --outcome success
```

检查顺序解码 H.264，输出每个 topic 的消息数、实测频率、最大时间间隔、长间隔次数（超过目标周期的 1.5 倍）、非递增时间戳、相机帧号缺口和缺失 topic。实际频率低于目标的 95% 会列入 warnings；该阈值用于诊断，不自动改成功标签。不要把 `--state-hz 200` 当作已录到 200 Hz。

导出使用 30 Hz 公共时间轴，因果选取每个时刻之前最近样本；样本过期（默认 100 ms）或重复相机帧会跳过该行，不插值、不复制图像。报告跳过行数，HDF5 记录来源和对齐策略。内存中只保留各流当前样本，不加载整段视频。

导出的 HDF5 可以交给现有回放、可视化和训练工具；回放仍执行原有轨迹校验，导出成功不表示能跳过回放安全检查。首版不支持直接对 MCAP 驱动机械臂回放。

MCAP 频率统计现在显示在终端原地刷新的状态区，不再每秒追加多行。ACTION 为动作频率，STATE 按左／右（及扩展臂）顺序显示反馈频率，CAM 按主／左／右（及扩展相机）顺序显示帧率；“调度跳期”为本条累计错过的控制周期数，不是相机丢帧数。完整统计仍保留在日志，真正的采集错误仍单独提示。

录制开始方式：按 Enter（或网页“准备下一条”）后先慢速对齐，随后等待扳机，不立即录制。拿稳主臂，按提示完成“全部松开 → 全部按到底 → 全部松开”的完整动作（当前映射：松开读数 ≥0.95、按下读数 ≤0.05；各阶段稳定 0.15 秒，最后还需从臂对齐稳定），看到“录制中”再做任务动作。等待时从臂慢速跟随，按下和松开的过程均不写入数据，文件与计时最后才开始；Esc/Ctrl+C 或网页停止仍可退出。每条数据都重新确认，HDF5 与 MCAP 相同；四臂模式需四个主臂扳机均完成按下和松开。开始后扳机恢复普通夹爪控制，松开不会结束录制。
